CAMPUSOS AI — COMPLETE MVP DOCUMENTATION
=========================================

Repository: vallabhatech/Rachoo
Purpose: Hackathon MVP for an agentic campus request-to-resolution platform.


1. WHAT WE ARE BUILDING
-----------------------
CampusOS AI is an AI-powered campus operations assistant that converts a student's natural-language request into an actionable workflow.

Core idea:
Student request -> AI understands -> workflow selected -> department routed -> staff action -> student gets resolution/status.

This is intentionally a focused MVP. The goal is to demonstrate meaningful agentic behavior and an end-to-end workflow rather than building a large production campus ERP.


2. MVP DEMO WORKFLOW
--------------------
Primary workflow: Bonafide Certificate.

Demo student message:
"I need a bonafide certificate for my internship."

The AI agent determines:
- Intent: BONAFIDE_CERTIFICATE
- Department: Academic Administration
- Priority: NORMAL
- Purpose: Internship application
- Next action: CREATE_REQUEST

The application then creates/routes the request.

Admin sees:
- Request ID #1024
- Bonafide Certificate
- Internship application
- Academic Administration
- Normal priority
- Pending Approval
- AI-generated summary

Admin can:
- Approve the request
- Reject the request

On approval:
- Status changes to Completed
- The UI reports that the student notification was sent

On rejection:
- Status changes to Rejected


3. WHY THIS IS AGENTIC
----------------------
The system is not only a chatbot.

The AI performs a workflow-oriented decision process:
1. Understand the natural-language request.
2. Identify the user's intent.
3. Extract useful context/purpose.
4. Determine priority.
5. Select the responsible department.
6. Select the next workflow action.
7. Create/routе the request in the application.
8. Preserve the result as workflow state for the admin/student UI.
9. Allow a human/admin to approve or reject the action.

This demonstrates AI + context + decision + tool/API execution + state + human approval.

10. GEMINI SETUP
----------------
Gemini is optional because the project includes a deterministic fallback.

Create a file named .env.local in the project root:

GEMINI_API_KEY=your_google_gemini_api_key

Then restart the development server.

IMPORTANT:
- Never commit .env.local.
- Never put the Gemini API key directly into frontend/client code.
- Keep secrets in environment variables.
- For Vercel, add GEMINI_API_KEY under the project's Environment Variables.

If Gemini is unavailable, the API route falls back to the demo Bonafide Certificate classification, so the presentation can still run.

14. API CONTRACT
----------------
Endpoint:
POST /api/agent

Request:
{
  "text": "I need a bonafide certificate for my internship."
}

Expected response shape:
{
  "intent": "BONAFIDE_CERTIFICATE",
  "department": "Academic Administration",
  "priority": "NORMAL",
  "purpose": "Internship application",
  "next_action": "CREATE_REQUEST"
}

The frontend consumes this structured response and displays the AI execution/workflow state.


15. DEMO FALLBACK
-----------------
The fallback exists specifically to protect the hackathon demo from an AI API/network/key problem.

If GEMINI_API_KEY is not configured or the Gemini response cannot be parsed, the API returns the deterministic Bonafide Certificate result.

Therefore:
- UI demo still works.
- Agent flow still appears.
- No API key is required for basic local demonstration.
- Gemini can be enabled when available.


16. CURRENT MVP LIMITATIONS
---------------------------
This is a hackathon MVP, not a production campus ERP.

Current limitations:
- No real authentication.
- No real student database.
- No persistent request database.
- Browser/in-memory state is used for the demo.
- No real certificate PDF generation.
- No real email/SMS/WhatsApp notification provider.
- Admin role switch is a demonstration mechanism.
- Only a small number of workflows are represented.
- No production-grade authorization model.
- No audit database.

These limitations are intentional to keep the MVP buildable and demoable within a very short time.

18. WHAT NOT TO BUILD FOR THE SHORT MVP
---------------------------------------
Do not spend the one-hour MVP window on:
- Kubernetes clusters
- Microservices
- Complex RAG pipelines
- Vector databases
- Custom authentication systems
- Payment systems
- Fifteen different workflows
- Native mobile apps
- Complex analytics
- Large admin ERP modules

The winning demo should show one workflow working end-to-end rather than many unfinished features.
